## 9. KForge (KForgeToken1785, `*KronD0` order kinds)

**Buy on the launchpad: PASS.** KForge's test front end is `testnet.kforge.xyz`, with the API `api-test.kforge.xyz`. A buy
takes two calls and no authentication:
1. `POST /buy/deposit {tokenId: <rung (curve) covenant id>, qty, buyer}` returns a P2SH deposit address and its cost.
2. The buyer pays that address in an ordinary transaction.
3. `POST /buy/execute` makes KForge's server build and submit the curve transaction.

Before paying, the script rebuilt the server's deposit address and the buyer's token script and checked that both matched
(`run/watch-dadd20e/launchpad/kforge-buy.cjs`).

testE bought 6 rungs of WHIT for 14.967 KAS. The token is `de92f1ae7fa20fc29a2bb4b56129cd699d06f85740f8ae473a017c7af529b2fe`;
one rung is 1,000,000 base units.
- The deposit: `1016fdaa1c2f638a93c3147a1a3848358e67f7c7c2813a6cd9ac22ea96a3289a`.
- The buy: `820f2ee91807f730807a55ba80289b63b79410cd9563c423f179f41dd319229e`.
- The buyer's token is output 5 (6,000,000 base units, 0.9 KAS carrier), and a 0.5 KAS "key" UTXO is output 6.

**B-14: the launchpad holding is id_type 1, which KOB does not spend.** The buyer's token is owned by id_type 1, not by the
buyer's pubkey (id_type 0). Its owner is the P2SH hash of a 5,585-byte script made for each buyer and token. KOB's profile and
the `*KronD0` builds serve id_type 0 only. Both indexers list the output with `owner_kind 1` and attribute it to no key:
- `kob balances` shows no WHIT.
- `kob place ... --side sell` stops with "you hold 0 [INSUFFICIENT_TOKENS]".
- The web's Balances shows nothing, and `#/market/de92f1ae...` says "Token not found" (`ui/hold.jsonl`, label `id1`).

That is correct for an output the key cannot spend alone. But nothing turns such a holding into one KOB can trade: no KOB tool
does it, and KForge's API offers buy, sell, swap, graduate and consolidate, with no withdraw or transfer. Every launchpad buyer
is in this position, so as shipped, KOB's KForge support cannot sell a token bought on the launchpad. The fixture
`observed-transfer.json` shows the same: its holder output has witness id_type `01`.

**The manual conversion.** We moved the holding to testE's x-only key at id_type 0 with a transaction built by hand and
checked input by input in KOB's script engine before submitting. Its construction is not published here (see the note on
KForge at the end of this section).

The transaction was accepted on the fourth attempt. All three rejections came from the hand-built transaction, not from KOB:
`4e1e1bf319fb4844b2f21ff765682421dc541a324a795549d7524e498314a8f1`. The indexers then list `4e1e1bf3...:0` as testE's
(`owner_kind 0`), and `kob balances` shows "WHIT: free 6 WHIT".

**Suggested fix (not done: it is a design choice).** Either a `kob` and web step that converts a KForge holding (token + key
UTXO -> id_type 0 holder), or id_type 1 inputs in the `*KronD0` placements.

## Bugs

**B-11 (LOW, web, FIXED d2df63f): a balance of a token with unknown decimals read as whole tokens.**
- Repro: Balances showing TUSD and an unregistered token of 500,000 base units.
- Cause: the row read "500,000.00000000". The column's fraction (8, from TUSD) was applied to base units (decimals 0 assumed),
  which reads as 500,000 tokens. The token has 2 decimals.
- Fix: tokens without a registry entry are left out of the column fraction and shown as "500,000 base units"
  (`balanceColumnFractions`, test).

**B-12 (LOW, soak checker, FIXED c3d709e): 4,754 false `all-in` errors from the imported history.**
- What happened: between 13:00 and 14:03 UTC on 2026-10-14, the checker reported every fill that `import-history.mjs` had
  copied (dadd20e). Each was a protocol v2 KobBid with `unlisted_reason history_import:*`, flagged "fill price beyond the
  order's worst bound (buy above)".
- Cause: these were IOC auctions whose price rose from `price` toward `lot_max`, and the import keeps only `price`. Example:
  `748765d2...` in the m9 database has price 2325360000 and lot_max 2336980000, and was filled at 2327393500.
- Fix: the checker no longer checks the fills of imported orders (`isImportedHistory`, test). They are chart history, not
  this run's transactions. The checker had already passed them, so the fix matters after the next import or replay.

**B-13 (LOW, web signer, FIXED a809c34): the frame dropped the price's scale for a token with unknown decimals.**
- Repro: the first order of an unlisted token. The frame read "Amount 1000 base units" and "Limit price 0.5 KAS", but the
  price is per 100 base units. The app's screen states the scale; the frame dropped that detail.
- Fix: the frame keeps the "per N base units of the token" detail (test). Verified live in section 9.

**B-14 (MEDIUM, KForge integration, OPEN): KOB cannot trade a KForge token bought on its launchpad.** Details in section 9.
- Cause: every launchpad holding is id_type 1 (a key script per buyer). KOB's KForge support spends id_type 0 only, and
  nothing converts one into the other.
- Repro: buy on `api-test.kforge.xyz`, then run `kob balances` or `kob place --side sell` ("you hold 0"), or open the token in
  the web ("Token not found").
- Workaround: the hand-made conversion transaction, `run/watch-dadd20e/launchpad/kforge-convert.cjs`.
