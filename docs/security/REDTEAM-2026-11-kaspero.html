2. The attacks

3. Findings

Router filler output by design

OUT-01 and OUT-03 on the 0.18 to 0.2 KAS output to the x402 payer in KasToToken buys and in x402 intent executions: whoever executes can redirect or shorten it.

Your answer: it is a filler that holds the output index open, not pinned on purpose; the payer's loss stays within max_extra.

34: OUT-01 19 (15 dump, 4 testnet), OUT-03 15 (dump)

Delivered cell carrier by design

OUT-03 on the 1 KAS carrier of the token cell the router delivers (KasToToken, TokenSwap, TokenToKas and their Kron versions): the executor can shorten it and keep the difference.

Your answer: max_extra is one cap, the payer's signed worst case; token amount, owner and extension are pinned, the carrier's KAS is not.

26: OUT-03 (22 dump, 4 testnet)

KForge-1785 refunds open

OUT-04 on 8 refunds and 1 close: the leftover is 0.028 KAS, exactly the request's refundTip (2,800,000), so almost certainly the tip. But this family's order coins don't match the zip's order programs, so the tool can't read the field and name it.

Question: which order build does the KForge-1785 family use?

9: OUT-04 (dump)

KRON sends open, tool side

OUT-02, OUT-03 and FEE-01 on two KRON send.tokens transactions. The KRON cells are the taker's, but KRON isn't a known program to the tool yet, so it can't see that the signer owns them and keeps the outputs protected.

Not a KOB question: KRON support is next on our side (the 2,433 B and 2,732 B programs you sent).

6: OUT-02 2, OUT-03 2, FEE-01 2 (dump)

Worth a line in KOB's docs

Because max_extra is a single unearmarked cap, whoever executes a router intent can always keep up to max_extra of the payer's KAS. That is safe as long as wallets set it tight; a high default hands executors a free margin. This is about use, not the covenant. Done on your side: the default max_extra is now computed from the intent's shape (carrier + 0.14 KAS for a single ask, was + 1 KAS).

4. What this does not cover

  • Matcher transactions from the source alone. Paths that need several orders in one transaction (a conditional's update, if-done exits, pair settles, router buy / sell legs) are not built by the search yet. 48 of 178 source paths stayed unexplored. Your dump covers these shapes as real transactions; that is where they were tested.
  • Token-aware attacks (FAM-10, BOR-01) ran only where the cell is the shipped KCC-20 reference build (198 attempts). The other builds, KRON included, were attacked through the generic input and output attacks only.
  • Signed paths on testnet (29 of 114: cancels, an amend, one intent creation, and the placements and merges, which the maker signs for their own token cell) were tested as an outsider: without the key, only changes that break the signature. The dump's listed keys covered the taker, matcher and keeper seats.
  • Not in the testnet set: a refund sent by the maker (keepers refund first; the payout is the maker's either way), and pair netting outside your soak (2 txs).
  • Consensus only. The judge is rusty-kaspa's consensus validator; mempool relay policy (standardness, minimum fees) is not applied.
